Automação e
Gerência de Configuração

Da configuração manual a uma infraestrutura reproduzível, versionada e verificável.

Infraestrutura como código Ansible · Docker · Nix · GitHub Actions
Tempo: 20 segundos. Apresentar o Grupo 04 e o objetivo: conectar os conceitos de automação a uma implantação real em uma VPS Debian.

01 · O problema

Quando o servidor depende da memória de alguém

Cenário proposto

Uma equipe configura servidores manualmente e comete erros.
Comando manual → Diferença entre ambientes → Incidente
01Erro humanoEtapas esquecidas ou executadas fora de ordem.
02InconsistênciaCada servidor termina com uma configuração diferente.
03Baixa repetibilidadeRecriar o ambiente leva tempo e gera incerteza.
04Sem rastreabilidadeNão existe histórico confiável do que mudou.

O problema não é apenas executar comandos — é garantir o mesmo resultado, sempre.

Fonte: documentação introdutória do Ansible
Tempo: 1 minuto. Começar pelo cenário oficial. Destacar que um procedimento manual pode funcionar uma vez, mas não garante consistência nem deixa evidência revisável.

Automação

Executa tarefas com intervenção humana mínima.

Gerência de configuração

Mantém sistemas aderentes a uma definição conhecida.

Infraestrutura como código

Representa infraestrutura em arquivos revisáveis e versionados.

Idempotência

Repetir a execução preserva o mesmo estado desejado.

estado atual+automação→estado desejado
Fontes: HashiCorp — Infrastructure as Code · Ansible — Playbooks
Tempo: 1 minuto e 10 segundos. Explicar que IaC permite revisão e versionamento. Idempotência não significa “não fazer nada”, mas fazer somente o necessário para alcançar o estado desejado.

04 · Ferramentas

Puppet e Chef: configuração em escala

P
Declarativo

Puppet

  • Recursos descrevem o estado desejado
  • Frequentemente usa servidor e agentes
  • Catálogos mantêm configurações padronizadas

Bom encaixe: frotas grandes e políticas centralizadas.

C
Receitas em Ruby

Chef

  • Receitas são agrupadas em cookbooks
  • Chef Infra Client aplica as políticas
  • Modelo flexível e orientado a código

Bom encaixe: equipes que precisam de lógica de configuração extensa.

Objetivo comumPacotes, serviços e arquivos permanecem no padrão definido.
Fontes: Puppet — Architecture · Chef Infra Client
Tempo: 50 segundos. Não tratar como concorrentes absolutos do Ansible. Puppet e Chef são fortes em convergência contínua e administração de muitos nós, frequentemente com agentes.

06 · Reprodutibilidade

Nix não é NixOS

N
Usado neste projeto

Nix

Gerenciador de pacotes e ambientes reproduzíveis.

  • Flakes
  • Dependências fixadas
  • Shell de desenvolvimento
≠
OS
Não usado na VPS

NixOS

Distribuição Linux configurada declarativamente.

  • Sistema por código
  • Gerações
  • Rollback
flake.nix→Ansible · actionlint · Docker CLI · Node.js→mesmo ambiente na CI

A VPS permanece Debian; Nix padroniza as ferramentas de desenvolvimento e automação.

Fontes: nix.dev · nixos.org
Tempo: 50 segundos. Corrigir a confusão comum: usamos Nix no runner e no desenvolvimento. A VPS não é convertida para NixOS e continua sendo administrada pelo Ansible sobre Debian.

- name: Detectar Docker existente
  ansible.builtin.command:
    argv: [docker, --version]
  register: docker_command
  failed_when: false

- name: Instalar Docker quando ausente
  ansible.builtin.apt:
    name: docker.io
  when: docker_command.rc != 0
site.yaml

Orquestra os três playbooks na ordem correta.

Decisão baseada no estadoO Docker do Coolify é preservado, evitando conflito entre containerd.io e os pacotes do Debian.

12 · Conclusão

Automação torna a mudança repetível

  • ✓Validação automática antes e depois

Limites atuais

  • —Uma única VPS, sem alta disponibilidade

  • —Protótipo com aplicação estática
  • —Adaptações necessárias para outras cargas
